### 1. Greg Isenberg：50 多人的公司，我跟 agent 说话比跟同事多（长帖）

- 原帖：[gregisenberg](https://x.com/gregisenberg/status/2117734977312047537)（北京时间 2026-11-04 05:45 发布）
- 数据：展示 687,938，点赞 5,602，收藏 16,259（收藏率约 2.36%），回复 545，转发 311，引用 139。昨天 18:30 约 38.3 万，本期新过线。
- 形态：长帖，约 3,400 字符

**全文翻译**

> 现在开公司感觉有点反乌托邦。我的团队有 50 多人，分布在 12 个国家，但我跟我的 agent 说话比跟人类同事还多。
>
> 给 grokbot 发语音笔记；用 mattpocock/skills 里的 /grill-me，让 agent 在动手之前先盘问这个想法；需求文档通过 Linear MCP 直接进 Linear；exa 加 firecrawl 的 agent 去读每个竞品的网站、定价页和更新日志；用 ideabrowser.com 找点子和趋势；apify 抓 G2、Reddit 和 App Store 的评论；prompt：「找出出现最多的 10 条抱怨，并引用用户原话」；用 context7，让 agent 在碰任何 API 之前先读最新文档。
>
> **设计**：Claude Code 加 Paper MCP；每个界面先出 4 个版本，再写第一行代码；从其中 2 个里挑一些部分让它合并，先发散再收敛；用 anthropic/skills 里的 frontend-design skill，加上我们自己的设计系统 skill；看到喜欢的界面就用 CleanShot 截图，直接丢进去说「做成这种感觉」。
>
> **构建**：用 pingdotgg/t3code 作为所有 agent 的控制台，手机上也能用；stablyai/orca 并行跑一队 agent，每个在自己的 git worktree 里；graphify 把整个代码库映射成知识图谱，让 agent 按图走而不是靠猜；headroom 在工具输出进模型之前先压缩，token 能多用 20% 到 95%；装 LSP 插件，让 agent 像 IDE 一样看到类型和报错；安全提示 hook 在高风险改动落地前先标出来；数据库用 Supabase MCP，计费用 Stripe；GitHub MCP 开 PR，Vercel 起预览环境；loop 通宵跑，我边喝咖啡边看上线了什么。
>
> **用户测试**：用 lightpanda 做无头浏览器，比 Chromium 轻得多，可以同时跑几百个；agent 像第一次来的用户一样，把预览环境里的每个流程都点一遍；一个人设没耐心，一个人设看不懂，一个人设在用手机；Playwright 加 Chrome DevTools MCP 做回归测试。
>
> **Bug**：Sentry MCP 抓到报错；agent 读堆栈，10 分钟内开出修复 PR；人只负责批准。
>
> **数据**：每天早上 7 点用 PostHog MCP 定时看昨天的漏斗；哪一步掉了超过 10%，agent 就去看 20 段会话录屏，告诉我原因；每周一 Stripe MCP 把所有取消订阅的原因汇总进一份文档。
>
> **agent 的工具**：orgo 让每个 agent 有自己的电脑；agentmail 让每个 agent 有自己的邮箱；agentphone 让我开车时能给它们打电话；composio connect-apps 接其他所有连接器；akitaonrails/ai-memory，一个用 git 管理的 Markdown wiki，让它们记得上周我们定了什么。
>
> **skills**：wshobson/agents 让 skill 在 Claude Code、Codex 和 OpenCode 之间通用；我的写作口吻；我们的设计系统；我们怎么写需求文档；skill creator，让 agent 自己写新 skill。
>
> **几个好用的技巧**：每个平台一个 agent，管 X 的 agent 从不碰邮件；分诊用便宜模型，凡是要上线的东西用 Opus；每个输出都由一个 LLM 评委打 1 到 10 分，低于 8 分打回去；每个 agent 每晚写一份 5 行日志，我 2 分钟就能读完整个公司；agent 犯的每个错都变成一个新 skill，这样同样的错只犯一次。
>
> **团队**：人类同事拿到的是第 5 版，不是我的语音笔记，他们对此挺满意，哈哈；他们的工作是给创意反馈、维护关系，以及告诉 agent 哪里做错了。人类 PM 每周看一次漏斗，这套东西每天早上看一次。
>
> 现在开公司，就是语音笔记加推理。

**为什么会传播**：开头一句反差（50 多个人，却跟 agent 说话更多）让人想知道他到底怎么做；后面按环节拆成清单，每一环读者都能对号入座。收藏 1.6 万远多于点赞 5,602，说明大家是存下来当清单用的。帖里的工具名单是作者自述，没有逐个核实；唯一的链接是作者自己的产品。

**写作可借鉴**：用「环节小标题 + 一行一个动作」写流程，每个动作尽量带一个数字或阈值（4 个版本、低于 8 分、掉超过 10%、20 段录屏、5 行日志），读者扫一眼就能抄走；最后用一句短话收尾（现在开公司，就是语音笔记加推理），方便转述。

**Issue 决策**：已新建 [Issue #115](https://github.com/geekjourneyx/agendum/issues/115)（READ · P2，含全文翻译、解读、拆解、总结和证据链；非 harness）。

### 2. OpenAI：自主漏洞发现、利用和修补流水线，一轮做出 948 个 Linux 内核提权补丁

- 数据：展示 1,275,000，点赞 8,776，收藏 3,078（收藏率约 0.24%），转发 914，引用 578，回复 490
- 形态：短帖，带一手数据，指向官网长文《A thousand fewer paths to root》

**全文翻译**

> 我们的安全研究员搭了一条自主的漏洞发现、利用和修补流水线。用一个即将推出的 cyber 模型跑了一轮，它在 Linux 内核里验证了 948 个本地提权漏洞并生成了补丁，API 总成本 120 万美元。

**为什么会传播**：一个数字组合（948 个内核提权、120 万美元）同时刺激了安全圈和 AI 圈，转发和引用比例高，很多人在争论「攻击是不是已经比防守便宜」。

**写作可借鉴**：一句话写清「谁做了什么、规模多大、花了多少钱」，三个硬数字放在一句里，细节全部留给长文，帖子只负责把人引过去。

**Issue 决策**：DEDUPED，已有 [Issue #114](https://github.com/geekjourneyx/agendum/issues/114)（今天 09:00 时段建立，已核对官网长文全文和分阶段成本，证据链里已经包含这条 X 帖），不重复建。

### 3. Anthropic：FlashProve，可验证某个回答确实出自某个模型

- 原帖：[AnthropicAI](https://x.com/AnthropicAI/status/2117710942826123294)（北京时间 2026-11-04 04:10 发布）
- 数据：展示 645,454，点赞 5,150，收藏 2,176（收藏率约 0.34%），回复 624，转发 536，引用 470。昨天 18:30 约 43.7 万，本期新过线。
- 形态：研究公告帖，约 1,000 字符，附完整技术文章和开源代码链接

**全文翻译**

> Anthropic 新研究：大语言模型「可证明推理」的进展。
>
> 我们在这里介绍 FlashProve。它建立在成熟的密码学技术之上，让开发者可以验证某个回答是否来自某个特定的 AI 模型。它比以往的开源方法高效得多。
>
> 这类证明有很多用途。比如，它能让攻击者更难劫持一段对话，也能让安全评估方确认，他们测试的模型和实际给用户服务的是同一个。
>
> 完整技术文章见此链接。
>
> 可证明推理的进一步进展，很可能是提升 AI 部署可信度的重要一环。为此我们开源了 FlashProve 的代码。
>
> 感谢合作者：Alessandro Chiesa、@GiacomoFenzi、@gwberg95、@miranda__christ、Rahul Dalal 和 Ben Mayer（@transmissions11）。

**为什么会传播**：「测的模型和卖的模型是不是同一个」是很多开发者一直怀疑的问题，这条给了一个可验证的技术答案，还开源了代码。

**写作可借鉴**：先用一句话说能力（验证回答出自哪个模型），再用两个具体场景说用途（防劫持对话、评估方核对模型），读者不懂密码学也能明白为什么重要。

**Issue 决策**：WATCH。属于推理基础设施研究，按纯模型和推理基础设施降权的规则，目前没有 1 到 2 小时能跑的实验切口；今天 09:00 和 10:00 时段已记为 WATCH。
