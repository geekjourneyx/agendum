### 1. OpenAIDevs：Pando，OpenAI monorepo 的新 Git 后端

- 原帖：[OpenAIDevs](https://x.com/OpenAIDevs/status/2117408792346509663)（北京时间 2026-11-03 08:09 发布）
- 数据：展示 863,301，点赞 4,974，收藏 2,180（收藏率约 0.25%）
- 形态：短帖，附一手工程长文 [Scaling Git at OpenAI](https://openai.com/index/scaling-git-at-openai)（2026-11-02，作者 Aaron Friel、Taylor Blau、Ted Nyman）
- 同题一手帖：[gdb](https://x.com/gdb/status/2117435285021810921) 说在考虑把 Pando 提供给外部；[thsottiaux](https://x.com/thsottiaux/status/2117412956950638872) 展示 496,056，差一点过线

**原帖中文翻译（全文）**

> 我们造了 Pando，一个给我们 monorepo 用的新 Git 后端，用来承接更多的 push 和 fetch，同时不改变我们的工程师和 agent 使用 Git 的方式。
>
> Pando 把推送延迟降低了约 80%，现在每天服务近 1 PB 的 Git 数据。我们可以让 Git 容量随 agent 用量一起增长。

**长文关键段落翻译（分节节译）**

> **为什么需要新系统**：Codex 改变了 OpenAI 的开发规模和节奏，工程师能并行做多得多的事。这意味着更多分支和推送、更多合并，以及来自开发环境、研究任务和 CI 的更多 fetch 和 clone。一个工程师现在同时有好几个改动等着跑 CI，每次推送又会让好几个任务去拉同一个 commit。从去年年底开始，系统跟不上了：fetch 和 push 变慢、合并失败，可靠性有时跌到 90% 以下。
>
> **放宽哪些约束**：大多数 Git 系统默认全仓库一致性和每个客户端专属的 packfile 是必须的。Pando 两件都放弃了：用较弱的因果一致性扩展写入，用复用 packfile 扩展读取。只有同时推送同一个 ref 的客户端才会冲突。
>
> **扩展推送**：传统 Git 服务器像亮出全部底牌的牌手，把所有分支都告诉客户端；分支上百万时，光是 ref 广播就可能超过 100 MiB。Pando 默认只广播主干。代价是分支要重发主干之外的内容，但实际 packfile 中位数小于 20 KiB，P99 小于 3 MiB。
>
> **按线速 fetch**：Pando 把客户端的 have 和 want 换算成一组已存的 packfile，用 Git 协议里很少人用的 packfile-uri 给出下载链接；区域缓存命中率超过 99%，普通云虚拟机就能跑满 10 Gbps。
>
> **怎么造出来的**：我们用 Codex 造 Pando，从立项到上线只用 10 周。核心由一名工程师设计，由多组 agent 实现，由少数几名工程师部署。我们写了一套一致性测试，让 agent 拿标准 Git 行为检验自己的改动；做了确定性模拟测试 harness 检查不变量、找竞态；用 GPT-6 Astra 让 agent 写 Lean 和 TLA+，形式化一套「Pando 理论」来找 bug、证明性质；多个连续会话跑了数百小时找边界情况；还有 agent 全天候做红队。
>
> **怎么上线**：先把 Pando 部署成旧系统前面的读写穿透代理，无停机迁移流量；写了准备 checkout 和引导 agent 使用新系统的 skill，开发者只要让 Codex 迁移自己的环境就行。切换后推送延迟中位数降近 80%，少量 CPU 核每天交付 1 PB，单小时服务过 57 TB，99% 以上来自本地缓存。

**详细总结**：文章的起点是一个很具体的因果：Codex 让一个人能同时推好几个分支，每次推送又触发好几个 CI 任务去拉代码，Git 服务端先被压垮。OpenAI 没有换掉 Git，只换后端，主动放弃「全仓库同一时间点一致」这个默认要求，换来分支之间互不等待。对 agent 工程更有用的是后半段：这个分布式系统主要由 agent 写成，团队配了一致性测试、确定性模拟、形式化证明、长时间边界搜索和持续红队五层验证，上线用代理双写兜底，迁移交给 skill。

**为什么会传播**：OpenAI 一手出品，数字硬（降 80%、每天 1 PB、10 周）；题目落在每个工程师都用的 Git 上，门槛低；「agent 用量把 Git 压垮」本身就是一个让人想转发的新现象；Greg Brockman 同时放出「可能对外提供」的钩子。

**写作可借鉴**：先用一句因果讲清问题从哪来（Codex 让并发变多，Git 先扛不住），再用一个比喻解释反常识的设计（服务器像亮出全部底牌的牌手），最后把「我们怎么造的」单独成节，写清楚哪些是人做的、哪些是 agent 做的、靠什么验证。人和 agent 的分工写得越具体，越可信。
